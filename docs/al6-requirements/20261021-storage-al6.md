# AL6 Requirements: Storage

- **Feature:** `storage` (Stage 1, substep 2)
- **AL7 source:** `docs/al7-intent/20261021-storage-al7.md`
- **Builds on:** `docs/al6-requirements/20261020-wikimapia-client-al6.md` (glossary reused) and `contracts/wikimapia-client.schema.ts` (the shapes the Client returns)
- **Status:** Ready for AL5 Contracts (revision 2: the stakeholder's answers to Q1 to Q6 are recorded as decisions D1 to D6 in section 5 and written into the criteria and rules)
- **Numbering note:** criteria AC-1 to AC-62 keep their numbers from revision 1. Criteria added in revision 2 are numbered AC-63 onwards and placed in the section they belong to.

## 0. Context and Scope

The Wikimapia Client (substep 1) can fetch Listing Pages and Place Details, but nothing is kept. This feature gives the project a **Place Store**: a local database that keeps every Place, its Comments (with Replies) and its Tags exactly as the Client reported them, so that the crawl (substep 3) can save what it fetches, the embedding step (substep 4) can read descriptions and comments, and search (Stage 2) can filter Places by area and by category.

**In scope**

- A Development Database and a separate Test Database, both with map-shape support and vector support, started together with the project's local services.
- Versioned Schema Setup that creates the storage for Places, Comments, Tags and Place-Tag links, and enables vector support.
- Saving a Listing Page (its Place Summaries) and saving the Place Details of one Place, both idempotent.
- Keeping Comments and Place-Tag Links that disappear from Wikimapia, marked as Gone, and marking them Present again if they come back.
- Reading one Place back with its Comments (and Replies) and Tags, each marked Present or Gone.
- Clear, named failures when the data is invalid or the Place Store cannot be reached.

**Out of scope**

- Embedding storage of any kind (substep 4). Vector support is enabled now, but nothing stores vectors yet.
- Crawl progress: which areas, pages or Places have been visited, scheduling, resuming (substep 3).
- Calling Wikimapia. The Place Store only receives what the Client already returned.
- Searching by area, by category or by meaning (Stage 2). This feature only has to keep the data in a form those searches can use.
- Deciding what to show of Places or Comments marked deleted or blocked, or of Gone Comments and Gone Place-Tag Links. They are kept with their marks; later stages decide.
- The link format of search result cards (`.agrules` section 2, Stage 2). The Wikimapia Link kept here is the attribution link of the stored Place, not a result card.

**Facts this document relies on** (from the Client AL6, the Client contract, and the trimmed fixtures in `contracts/fixtures/wikimapia/`):

- A Place Summary carries Place ID, name, Wikimapia Link, Location (centre and bounds, no address) and Outline. It carries no description, Tags, Comments, flags or parent.
- Place Details carry Place ID, title, description, Tags, Parent Place ID (absent when none), building/region/deleted marks, Wikipedia link (when present), Outline, Location with optional address items, and Comments. They carry **no** Wikimapia Link.
- Recorded Outlines are open lists of points: the last point is not a repeat of the first (Place 1381893 has 4 points, Place 62587 has 19).
- Descriptions range from a few characters ("Belgrade,Serbia.") to several thousand, and contain non-Latin letters (Cyrillic "Трг Републике", "Đinđić") and line breaks. Comment messages may end in a carriage return and line break.
- In the reconstructed nested-replies fixture (`getbyid-62587-nested-replies.json`), the Reply to a Reply ("Paul") carries Place ID 55 and comment number 5 while sitting under Place 62587. Real Wikimapia data has never shown this. Under decision D5 such data is rejected, so storage tests of nesting use a synthetic example with matching Place IDs (AC-34), and use this fixture only to check the rejection (AC-38).
- Comment numbers seen so far are distinct within one Place (1 and 2 for Place 62587).

## 1. Ubiquitous Language (Domain Glossary)

Terms already defined in the Client AL6 keep their meaning: **Place, Place ID, Place Summary, Place Details, Listing Page, Tag, Outline, Location, Comment, Reply, Comment Author, Commenter IP, Wikimapia Client (the Client)**. New or refined terms:

| Term | Definition |
|---|---|
| **Place Store** | The component specified here: the project's own local database of Places, Comments and Tags, plus the functions that save into it and read from it. Nothing outside the Place Store reads or writes the stored data directly. |
| **Operator** | The person or job that uses the Place Store (in practice the crawl jobs of substep 3, and the developer running them). Same role as in the Client AL6. |
| **Development Database** | The Place Store instance the developer works with locally. |
| **Test Database** | A separate Place Store instance used only by automated tests. Tests never touch the Development Database. |
| **Schema Setup** | The ordered, versioned list of steps that prepares an empty database to be a Place Store (creates the storage for Places, Comments, Tags and Place-Tag links, and enables map-shape and vector support). Each step can be applied and undone. |
| **Vector Support** | The database capability that later steps use to store and compare embeddings. Enabled by Schema Setup in this feature; no embedding is stored yet. |
| **Stored Place** | Everything the Place Store holds about one Place, as it is read back: Place ID, Wikimapia Link, Place Name, Location, Outline, and, once its details have been saved, description, building/region/deleted marks, Parent Place ID (when any), Wikipedia link (when any), address items (when any), Tags and Comments (each with its Presence Mark) and the Details Fetched At moment. |
| **Place Name** | The single name the Place Store keeps for a Place. On a Summary-Only Place it is the Place Summary's name; on a Detailed Place it is the title from the most recently saved Place Details (rule 3, decision D1). |
| **Wikimapia Link** | The link to the Place's page on Wikimapia, kept for attribution and linking back (CC BY-NC-SA 3.0). Every Stored Place has one. It is either a Listing Link or a Built Link. |
| **Listing Link** | A Wikimapia Link as given in a Place Summary (e.g. `http://wikimapia.org/1381893/University-Park`). |
| **Built Link** | The Wikimapia Link the Place Store forms itself, exactly `http://wikimapia.org/<Place ID>` (e.g. `http://wikimapia.org/1381893`), for a Place first saved from Place Details, which carry no link (decision D6). A later Listing Save replaces it with the Listing Link. |
| **Summary-Only Place** | A Stored Place for which a Place Summary has been saved but no Place Details yet. Its details items are absent and its Tags and Comments are empty. |
| **Detailed Place** | A Stored Place for which Place Details have been saved at least once. |
| **Details Fetched At** | The moment (to the second, UTC) at which the Place Details being saved were fetched from Wikimapia. Given by the Operator with every details save; absent on a Summary-Only Place. |
| **Outline Shape** | The Outline kept as a closed map shape in standard GPS longitude/latitude (WGS 84), so that later stages can test whether a Place lies in or near an area. Wikimapia's open list of points is closed by joining the last point back to the first; reading back returns the points as given, without the closing repeat. Only Outlines of 3 or more points get an Outline Shape (decision D4). |
| **Centre Point** | The Location's centre (longitude, latitude) kept as a map point in WGS 84, for distance and area tests by later stages. Every Stored Place has one. |
| **Tag Catalogue** | The list of all Tags (id and title) the Place Store has seen, each kept once, shared by all Places. Tags are never removed from it. |
| **Place-Tag Link** | The fact that a given Tag is or was attached to a given Place. Carries a Presence Mark. Search in Stage 2 filters Places by these links. |
| **Comment Key** | A Comment is identified by the Place it belongs to together with its comment number. Two Comments of one Place never share a comment number, whether Present or Gone. |
| **Parent Comment** | For a Reply, the Comment (or Reply) it is listed under. Replies are stored as Comments of the same Place that point to their Parent Comment; top-level Comments have none. Reading back rebuilds the nesting. A Gone Comment keeps the Parent Comment it had when it was last Present. |
| **Presence Mark** | A mark on every stored Comment (including Replies) and every Place-Tag Link of a Detailed Place: either **Present** or **Gone** (decision D2). Read back with the item. |
| **Present** | The Comment or Place-Tag Link was contained in the most recently saved Place Details of its Place. |
| **Gone** | The Comment or Place-Tag Link was contained in some earlier Place Details of its Place but not in the most recently saved ones. It is kept with the values it had when it was last Present. Gone is the Place Store's own mark; it is not Wikimapia's deleted or blocked mark, which are kept separately as reported. |
| **Listing Save** | Saving all Place Summaries of one Listing Page. |
| **Details Save** | Saving the Place Details of one Place, together with its Details Fetched At. |
| **Save Outcome** | What a save reports for each Place it touched: **Created** (the Place was not stored before), **Updated** (something stored about it changed, including a Presence Mark or the Wikimapia Link, but not Details Fetched At alone) or **Unchanged** (everything else already matched). |
| **Idempotent** | Saving the same data again leaves the Place Store exactly as it was (apart from a later Details Fetched At, rule 5) and reports every Place as Unchanged. |
| **Store Failure** | Any outcome where the Place Store cannot complete a save or a read. Always one of the named kinds below. |
| **Invalid Data** | Kind of Store Failure: the data given to a save does not have the shape of a Place Summary, Listing Page or Place Details (as defined by the Client), or breaks a rule of this document (for example two Comments with the same comment number, or a Comment carrying another Place's ID). Names the offending item. Nothing is saved. |
| **Store Unavailable** | Kind of Store Failure: the Place Store could not be reached or could not complete the operation. Nothing is saved. |
| **Place Not Found** | The answer to reading back a Place ID that is not stored. Not a failure. |

## 2. User Stories

- **US-1 (Keep listed places):** As an Operator, I want to save a whole Listing Page in one step, so that every Place found in an area is known to the project even before its details are fetched.
- **US-2 (Keep place details):** As an Operator, I want to save the Place Details of one Place, with its Comments and all their Replies and its Tags, and record when they were fetched, so that the full, current picture of the Place is kept and I can tell which Places still need (re)fetching.
- **US-3 (Safe to repeat):** As an Operator, I want saving the same data again to change nothing and to tell me so, so that a crawl can be rerun or resumed without creating duplicates or churn.
- **US-4 (Read a place back):** As a developer of the embedding and search steps, I want to read one Place back with its Comments (nested as Replies) and Tags in the same shapes the Client uses, each marked Present or Gone, so that later steps work with one familiar form of data and can choose whether to use items no longer on Wikimapia.
- **US-5 (Ready for spatial and category search):** As the search developer (Stage 2), I want each Place's Outline and Centre Point kept as map shapes and its Tags kept as links to a shared Tag Catalogue, so that search can filter Places by area and by category.
- **US-6 (Privacy and licensing):** As the project owner, I want the Place Store to have no place for Commenter IPs and to keep Comment Authors and a Wikimapia Link for every Place, so that we hold no personal data we do not need and can credit Wikimapia and its authors as CC BY-NC-SA 3.0 requires.
- **US-7 (Reproducible setup and tests):** As a developer, I want the databases started with the project's local services, prepared only by versioned Schema Setup, and tests run against a separate Test Database, so that anyone can rebuild the Place Store from nothing and tests never damage development data.
- **US-8 (Clear failures, no half-saves):** As an Operator, I want every failed save reported as a named Store Failure with nothing partially saved, so that the crawl can skip or retry a Place without leaving it in a mixed state.
- **US-9 (Nothing seen is lost):** As the project owner, I want Comments and Tags that disappear from Wikimapia to be kept and marked Gone rather than erased, so that the project keeps everything it has seen and can tell what is still on Wikimapia.

## 3. Acceptance Criteria (BDD Style)

Test inputs are Client-shaped values (Place Summaries, Listing Pages, Place Details). Where a criterion names a fixture, the input is the Client's reading of that trimmed fixture from `contracts/fixtures/wikimapia/`, or a small synthetic value with the same field values (`.agrules` section 4).

### 3.1 Databases and Schema Setup (US-7)

- **AC-1 (Two databases):** Given the project's local services are started, When the developer looks at the available databases, Then a Development Database and a separate Test Database are both running, each with map-shape support and Vector Support available.
- **AC-2 (Setup from nothing):** Given an empty database, When Schema Setup is applied, Then the database can hold Places, Comments, the Tag Catalogue and Place-Tag Links (Comments and Place-Tag Links each with a Presence Mark), and Vector Support is enabled, without any step done by hand.
- **AC-3 (Setup repeated):** Given a database on which Schema Setup has already been fully applied, When Schema Setup is applied again, Then no step is applied a second time and no stored data changes.
- **AC-4 (Setup undone):** Given a database on which Schema Setup has been fully applied, When every step is undone, Then the storage for Places, Comments, Tags and Place-Tag Links no longer exists; and applying Schema Setup again afterwards succeeds as in AC-2.
- **AC-5 (No embeddings, no crawl progress yet):** Given Schema Setup has been applied, When the stored structure is inspected, Then it has no place for embeddings or vectors of any kind and no place for crawl progress (visited areas, pages or Places); Vector Support is enabled but unused.
- **AC-6 (No place for Commenter IPs):** Given Schema Setup has been applied, When the stored structure for Comments is inspected, Then it has no place for a Commenter IP in any form, and it does have a place for the Comment Author.

### 3.2 Saving a Listing Page (US-1, US-3, US-5, US-6)

- **AC-7 (Happy path, new Places):** Given an empty Place Store and the Listing Page from `box-belgrade-page1.json` (Places 1381893, 62587 and 164369), When the Operator performs a Listing Save, Then all three Places are stored as Summary-Only Places, the Save Outcome reports each of them as Created, and nothing else is stored.
- **AC-8 (Summary content kept):** Given the Listing Save of AC-7, When Place 1381893 is read back, Then it has Place Name "University Park", Wikimapia Link `http://wikimapia.org/1381893/University-Park`, Centre Point longitude 20.457876 and latitude 44.819524, bounds north 44.820321, south 44.818727, east 20.459064, west 20.456688, an Outline of exactly the same 4 points in the same order (first point longitude 20.456688, latitude 44.8198), no address items, no description, no building/region/deleted marks, no Parent Place ID, no Wikipedia link, no Details Fetched At, no Tags and no Comments.
- **AC-9 (Listing Save is idempotent):** Given the Listing Save of AC-7 has been done, When the same Listing Page is saved again, Then every Stored Place reads back exactly as before, no Place, Comment or Tag is added or removed, and the Save Outcome reports all three Places as Unchanged.
- **AC-10 (Listing Save updates a Summary-Only Place):** Given Place 1381893 is a Summary-Only Place, When a Listing Page is saved in which its name, Wikimapia Link, Location or Outline differs from what is stored, Then the Stored Place takes the new values and the Save Outcome reports it as Updated.
- **AC-11 (Details take precedence over a listing, D1):** Given Place 62587 is a Detailed Place (saved from `getbyid-62587.json`), When a Listing Page is saved in which Place 62587 has a different name, Location and Outline from the stored ones, Then its Place Name, Location, Outline, Outline Shape, Centre Point, description, marks, Parent Place ID, Wikipedia link, address items, Tags, Comments (with their Presence Marks) and Details Fetched At all read back unchanged; only its Wikimapia Link is taken from the Place Summary. The Save Outcome reports the Place as Updated if the Wikimapia Link changed, and as Unchanged otherwise (differences in name, Location or Outline alone do not count).
- **AC-12 (Empty Listing Page):** Given a Listing Page with no Place Summaries (the Client's reading of `box-belgrade-empty-page.json`), When the Operator performs a Listing Save, Then nothing in the Place Store changes, the Save Outcome lists no Places, and no failure is reported.
- **AC-13 (Same Place twice in one page):** Given a Listing Page that lists the same Place ID twice, When the Operator performs a Listing Save, Then the Place is stored once, with the values of its last occurrence in the page, and the Save Outcome reports it once.
- **AC-14 (Listing Page totals not stored):** Given any Listing Save, When the Place Store is inspected, Then the page number, page size and Total Found of the Listing Page are not stored (they belong to crawl progress, substep 3).
- **AC-15 (Listing Save is all or nothing):** Given a Listing Page in which one Place Summary is Invalid Data (for example a Place ID that is not a positive whole number, or a Wikimapia Link that does not point to that Place), When the Operator performs a Listing Save, Then the Place Store reports Invalid Data naming that Place Summary and the offending item, and none of the page's Places is saved or changed.
- **AC-63 (Listing Link replaces a Built Link, D1 and D6):** Given Place 1381893 was saved only from its Place Details and has the Built Link `http://wikimapia.org/1381893`, When a Listing Page containing Place 1381893 with Wikimapia Link `http://wikimapia.org/1381893/University-Park` is saved, Then the Place reads back with Wikimapia Link `http://wikimapia.org/1381893/University-Park`, everything else about it is unchanged (as in AC-11), and the Save Outcome reports it as Updated.

### 3.3 Saving Place Details (US-2, US-3, US-5, US-6, US-9)

- **AC-16 (Happy path, new Place with Comments):** Given an empty Place Store and the Place Details of Place 62587 from `getbyid-62587.json`, with Details Fetched At 2026-10-21 10:00:00 UTC, When the Operator performs a Details Save, Then Place 62587 is stored as a Detailed Place, the Save Outcome reports it as Created, and reading it back gives: Place Name "Square of the Republic", Wikimapia Link `http://wikimapia.org/62587` (a Built Link, AC-31), the full description unchanged character for character (including "Трг Републике", "Đinđić" and every line break), Tags "historic town square" (id 44926) and "town square" (id 46360), both Present, no Parent Place ID, not a building, not a region, not deleted, Wikipedia link `http://en.wikipedia.org/wiki/Republic_Square_(Belgrade)`, an Outline of the same 19 points in the same order, Centre Point longitude 20.4603516 and latitude 44.8161006 with the recorded bounds, address items country "Serbia and Montenegro", state "Central Serbia", place "Belgrade", city "Belgrade" and no street or house number, Details Fetched At 2026-10-21 10:00:00 UTC, and exactly 2 Comments in the order given, both Present.
- **AC-17 (Comments kept in full):** Given the Details Save of AC-16, When Place 62587 is read back, Then its first Comment has comment number 1, Comment Author "Mateja", author user id 0, no author photo link, message "Everybodey is waiting for someone here", 5 good and 15 bad votes, not blocked, not deleted, posted at 1169755601 seconds after 1970-01-01 00:00 UTC, moderator id 0, no moderator name, no Replies and Presence Mark Present; and its second Comment has comment number 2, Comment Author "Serbia", author user id 150331, author photo link `/p/u/00/00/15/03/31_50.jpg`, message "Najbolji trg na svetu!!", 33 good and 0 bad votes, posted at 1199388051, no Replies and Presence Mark Present.
- **AC-18 (Round trip):** Given any valid Place Details D saved with Details Fetched At T into a Place Store where the Place was not stored, When the Place is read back, Then the Place ID, title (as Place Name), description, Tags, Parent Place ID, marks, Wikipedia link, Outline, Location and Comments (with Replies nested as in D, in the same order) are identical to D, every Comment, Reply and Tag is marked Present, absent items in D are absent (not empty) when read back, the Wikimapia Link is the Built Link for that Place ID, and Details Fetched At equals T.
- **AC-19 (Place without Comments):** Given the Place Details of Place 1381893 from `getbyid-1381893.json`, When the Operator performs a Details Save, Then reading it back gives Place Name "University Park", description "Belgrade,Serbia.", Tag "park" (id 194, Present), no Wikipedia link, no street, no house number, and an empty list of Comments; no failure is reported.
- **AC-20 (Details complete a Summary-Only Place):** Given Place 1381893 is a Summary-Only Place saved by AC-7, When its Place Details are saved, Then it becomes a Detailed Place, the Save Outcome reports it as Updated, its Place Name, Location and Outline are now those of the Place Details, and its Wikimapia Link is still the Listing Link `http://wikimapia.org/1381893/University-Park` (a Details Save never replaces a stored Wikimapia Link).
- **AC-21 (Details Save is idempotent):** Given Place 62587 has been saved from Place Details D with Details Fetched At T, When D is saved again with the same T, Then the Stored Place reads back exactly as before, no Comment, Tag or Place-Tag Link is added, removed or changes its Presence Mark, and the Save Outcome reports it as Unchanged.
- **AC-22 (Re-fetched, nothing changed, D3):** Given Place 62587 has been saved from Place Details D with Details Fetched At T, When the same D is saved with a later Details Fetched At T2, Then only the Details Fetched At changes, to T2; everything else (including every Presence Mark and the Wikimapia Link) reads back exactly as before, and the Save Outcome reports the Place as Unchanged.
- **AC-23 (Details changed on Wikimapia):** Given Place 62587 has been saved from Place Details D, When Place Details D2 are saved that differ from D in description, title, marks, Outline, Location, address items or Wikipedia link, Then the Stored Place reads back with the values of D2 and the Save Outcome reports it as Updated.
- **AC-24 (Optional items removed on Wikimapia):** Given a Detailed Place whose stored details include a Wikipedia link, a Parent Place ID and a street, When Place Details that lack those items are saved, Then those items read back as absent. (Only Comments and Place-Tag Links are kept as Gone; other details items always follow the most recent Place Details.)
- **AC-25 (Comment changed):** Given Place 62587 has been saved with its 2 Comments, When Place Details are saved in which Comment number 1 has a different message, vote counts, deleted mark or blocked mark, Then Comment number 1 reads back with the new values, Comment number 2 is unchanged, both stay Present, and the Save Outcome reports the Place as Updated.
- **AC-26 (Comment added):** Given Place 62587 has been saved with its 2 Comments, When Place Details are saved that contain those 2 Comments plus a new Comment number 3, Then the Place reads back with all 3 Comments in the order given, all Present, and the Save Outcome reports the Place as Updated.
- **AC-27 (Comments and Tags no longer on Wikimapia are kept as Gone, D2):** Given Place 62587 has been saved with Comments number 1 and 2 and Tags 44926 "historic town square" and 46360 "town square", When Place Details are saved that contain only Comment number 2 and only Tag 46360, Then the Place reads back with both Comments and both Tags: Comment number 2 and Tag 46360 marked Present, Comment number 1 and Tag 44926 marked Gone; Comment number 1 keeps every value it had when last Present (author, message, votes, marks, posted moment); Tag 44926 remains in the Tag Catalogue; and the Save Outcome reports the Place as Updated.
- **AC-64 (Gone items are idempotent):** Given the save of AC-27 has been done, When the same Place Details (only Comment number 2 and Tag 46360) are saved again, with the same or a later Details Fetched At, Then Comment number 1 and Tag 44926 are still kept and still Gone, nothing else changes (except Details Fetched At under AC-22), and the Save Outcome reports the Place as Unchanged.
- **AC-65 (Gone items come back):** Given the save of AC-27 has been done, When Place Details are saved that again contain Comment number 1 and Tag 44926, Then Comment number 1 and Tag 44926 read back as Present, Comment number 1 takes the values given in these Place Details (for example a changed message or vote count) and the position they give it, Comment number 1 is stored only once, and the Save Outcome reports the Place as Updated.
- **AC-66 (Gone Reply):** Given a Place saved with the nesting of AC-34 ("Mateja" with Reply "Serbia", which has Reply "Paul"), When Place Details are saved that contain "Mateja" and "Serbia" in the same nesting but no "Paul", Then reading back shows "Paul" still as a Reply of "Serbia", marked Gone, with all its saved values; "Mateja" and "Serbia" are Present.
- **AC-67 (Gone Comment with Replies):** Given a Place saved with the nesting of AC-34, When Place Details are saved that contain only "Paul" (number 5) as a top-level Comment, Then reading back shows "Paul" at the top level, Present; "Mateja" at the top level, Gone, with Reply "Serbia", Gone, which now has no Replies; and the Save Outcome reports the Place as Updated.
- **AC-68 (All Comments gone):** Given Place 62587 has been saved with its 2 Comments, When Place Details with no Comments are saved, Then both Comments are kept and read back as Gone, and no failure is reported.
- **AC-28 (Deleted Place kept):** Given Place Details marked deleted, When the Operator performs a Details Save, Then the Place is stored and reads back with the deleted mark set; no failure is reported.
- **AC-29 (Deleted or blocked Comment kept):** Given Place Details containing a Comment or Reply marked deleted or blocked, When the Operator performs a Details Save, Then that Comment or Reply is stored and reads back with its mark set, marked Present, together with its own Replies.
- **AC-30 (Parent Place not stored):** Given Place Details with Parent Place ID 999 where Place 999 is not stored, When the Operator performs a Details Save, Then the Place is saved and reads back with Parent Place ID 999, and Place 999 is not created.
- **AC-31 (Details-only Place gets a Built Link, D6):** Given an empty Place Store, When the Place Details of Place 1381893 are saved without any earlier Listing Save, Then the Place is stored as a Detailed Place and reads back with Wikimapia Link exactly `http://wikimapia.org/1381893`; saving the same Place Details again leaves the link unchanged and reports Unchanged. A later Listing Save replaces it with the Listing Link (AC-63).
- **AC-32 (Long and non-Latin text):** Given Place Details whose description is at least 7,000 characters long and contains Cyrillic and Latin letters with diacritics, line breaks and HTML entities such as `&quot;`, and a Comment message ending in a carriage return and line break, When saved and read back, Then the description and the message are identical character for character, with nothing cut, trimmed or decoded.
- **AC-33 (Empty description):** Given Place Details whose description is empty text, When saved and read back, Then the description reads back as empty text and no failure is reported.

### 3.4 Comment Replies (US-2, US-4, US-6)

All nesting criteria use a small synthetic example in which every Comment and Reply carries Place ID 62587 (decision D5).

- **AC-34 (Replies stored and rebuilt):** Given Place Details of Place 62587 in which Comment number 1 ("Mateja") has one Reply, Comment number 2 ("Serbia"), which itself has one Reply, Comment number 5 ("Paul"), all three carrying Place ID 62587, When the Details are saved and the Place is read back, Then it has exactly 1 top-level Comment ("Mateja"), whose Replies contain exactly "Serbia", whose Replies contain exactly "Paul", each with all the fields it was saved with and marked Present, and "Paul" has no Replies.
- **AC-35 (Each Reply is a Comment of the Place):** Given the save of AC-34, When the Comments of Place 62587 are counted, Then there are 3 Comments, each identified by Place 62587 and its comment number (1, 2, 5), each Reply recording its Parent Comment ("Serbia" under 1, "Paul" under 2), and "Mateja" recording none.
- **AC-36 (Order of Replies):** Given a Comment with several Replies, When saved and read back, Then the Replies appear in the order they were given.
- **AC-37 (Reply moved):** Given a Place saved with the nesting of AC-34, When Place Details are saved in which "Paul" (number 5) is a top-level Comment instead of a Reply of "Serbia", Then reading back shows "Paul" at the top level and "Serbia" with no Replies, all Present, and the Save Outcome reports the Place as Updated.
- **AC-38 (Comment from another Place rejected, D5):** Given Place Details of Place 62587 containing a Comment or Reply, at any depth, whose own Place ID is not 62587 (as in `getbyid-62587-nested-replies.json`, where "Paul" carries Place ID 55), When the Operator performs a Details Save, Then the Place Store reports Invalid Data naming that Comment's comment number and its Place ID, and nothing is saved.
- **AC-39 (Duplicate comment number):** Given Place Details in which two Comments or Replies, at any depth, carry the same comment number, When the Operator performs a Details Save, Then the Place Store reports Invalid Data naming the duplicated comment number, and nothing is saved.

### 3.5 Tags and categories (US-2, US-5)

- **AC-40 (Shared Tag Catalogue):** Given Place 62587 (Tags 44926 "historic town square", 46360 "town square") is saved, and then another Place whose Tags include 46360 "town square" is saved, When the Tag Catalogue is inspected, Then Tag 46360 appears in it exactly once, and both Places are linked to it.
- **AC-41 (Places of a Tag):** Given the saves of AC-40, When the Place-Tag Links for Tag 46360 are inspected, Then exactly those two Places are linked to it, both links Present, and Place 62587 is also linked to Tag 44926, Present.
- **AC-42 (Tag title changed on Wikimapia):** Given Tag 194 is stored with title "park", When Place Details are saved in which Tag 194 has the title "city park", Then Tag 194 reads back as "city park" for every Place linked to it, whether the link is Present or Gone.
- **AC-43 (Same Tag twice in one Place):** Given Place Details that list the same Tag id twice, When saved, Then the Place is linked to that Tag once and no failure is reported.
- **AC-69 (Gone link to a shared Tag):** Given the saves of AC-40, When new Place Details of Place 62587 are saved without Tag 46360, Then Place 62587's link to Tag 46360 is Gone, the other Place's link to Tag 46360 is still Present, and Tag 46360 is still in the Tag Catalogue once.

### 3.6 Map shapes (US-5)

- **AC-44 (Outline kept as a closed shape):** Given Place 62587 saved with its 19-point Outline, When the stored Outline Shape is examined, Then it is a closed shape in WGS 84 longitude/latitude whose boundary visits the 19 given points in order and then returns to the first; and reading the Place back returns exactly the 19 given points, without a repeated closing point.
- **AC-45 (Centre Point kept):** Given any saved Place, When its stored Centre Point is examined, Then it is a WGS 84 point at the Location's centre longitude and latitude.
- **AC-46 (Outline already closed):** Given an Outline whose last point repeats its first, When saved and read back, Then the Outline reads back exactly as given (with the repeated point) and the stored Outline Shape is closed without adding another repeat.
- **AC-47 (Unusual but drawable Outline):** Given an Outline of 3 or more points whose boundary crosses itself, When saved, Then the Place is saved, the Outline reads back exactly as given, and no failure is reported (Wikimapia's drawings are kept as they are).
- **AC-48 (Outline too small for a shape, D4):** Given a Place Summary or Place Details whose Outline has fewer than 3 points (2, 1 or none), When saved, Then the Place is saved with its Centre Point and no Outline Shape, the Outline reads back exactly as given (possibly empty), and no failure is reported.
- **AC-70 (Outline grows or shrinks):** Given a Place stored with an Outline Shape, When it is saved again (by a save that may change its Outline, see AC-10 and AC-11) with an Outline of fewer than 3 points, Then it no longer has an Outline Shape; and given a Place stored without an Outline Shape, When it is saved with an Outline of 3 or more points, Then it has one, as in AC-44.

### 3.7 Reading a Place back (US-4, US-9)

- **AC-49 (Read back form):** Given any Stored Place, When it is read back, Then its Location, Outline, Tags and Comments (with Replies nested) are reported in the same shapes the Client uses for Place Summaries and Place Details, with one addition: every Tag and every Comment and Reply carries its Presence Mark (Present or Gone). The Place also carries its Place Name, its Wikimapia Link (always) and Details Fetched At (when the Place is a Detailed Place).
- **AC-71 (Read back returns Present and Gone together, D2):** Given a Detailed Place that has both Present and Gone Comments and Tags, When it is read back, Then a single read returns all of them, each marked; nothing is hidden, and a reader that wants only what is still on Wikimapia keeps the items marked Present. There is no separate read that leaves out Gone items.
- **AC-50 (Place Not Found):** Given Place ID 424242 is not stored, When it is read back, Then the Place Store answers Place Not Found, not a failure.
- **AC-51 (Invalid Place ID on read):** Given a Place ID that is zero, negative or not a whole number, When it is read back, Then the Place Store reports Invalid Data and does not consult the stored data.
- **AC-52 (Order of Comments):** Given a Detailed Place, When it is read back, Then among the top-level Comments, and among the Replies of every Comment, the Present ones come first, in the order they had in the most recently saved Place Details, followed by the Gone ones in ascending comment number. A Gone Comment or Reply appears under the Parent Comment it had when it was last Present (or at the top level if it had none).
- **AC-72 (Order of Tags):** Given a Detailed Place, When it is read back, Then its Present Tags come first, in the order of the most recently saved Place Details, followed by its Gone Tags in ascending Tag id.

### 3.8 Failures, atomicity and privacy (US-6, US-8)

- **AC-53 (Wrong shape rejected):** Given input to a Listing Save or Details Save that lacks a required item (for example Place Details without a title, or a Comment without a Comment Author) or has an item of the wrong kind (for example a vote count that is not a whole number, or a longitude outside -180..180), When the save is attempted, Then the Place Store reports Invalid Data naming the offending item (including its position inside Comments or Replies), and nothing is saved.
- **AC-54 (Commenter IP refused):** Given Place Details in which a Comment or Reply at any depth carries a Commenter IP (`user_ip` or any other spelling), When a Details Save is attempted, Then the Place Store reports Invalid Data, nothing is saved, and the Commenter IP value does not appear in the failure's message or details.
- **AC-55 (Missing Details Fetched At):** Given a Details Save without a Details Fetched At, or with one that is not a valid moment, When it is attempted, Then the Place Store reports Invalid Data and nothing is saved.
- **AC-56 (Details Save is all or nothing):** Given Place 62587 is stored with Details D, When a Details Save of new Details D2 fails part way (for example the Place Store becomes unavailable after some Comments were written or marked Gone), Then Place 62587 reads back exactly as D, with none of D2 applied and every Presence Mark as before.
- **AC-57 (Store Unavailable):** Given the Place Store cannot be reached, When any save or read is attempted, Then a Store Unavailable failure is reported, and the failure's message and details contain no database password or connection secret.
- **AC-58 (Failures change nothing):** Given any Store Failure of any kind on a save, When the Place Store is inspected afterwards, Then every Stored Place, Comment, Tag, Place-Tag Link and Presence Mark is exactly as it was before the save.
- **AC-59 (Attribution kept):** Given any Stored Place, When it is read back, Then it carries a Wikimapia Link (a Listing Link if a Listing Save has supplied one, otherwise its Built Link), and every Comment and Reply, Present or Gone, carries its Comment Author.

### 3.9 Tests (US-7, `.agrules` section 4)

- **AC-60 (Test Database only):** Given the automated tests that need a database, When they run, Then they use only the Test Database, and the Development Database is unchanged afterwards.
- **AC-61 (Known starting state):** Given any such test, When it starts, Then the Test Database has Schema Setup fully applied and holds no Places, Comments, Tags or Place-Tag Links other than those the test itself saves.
- **AC-62 (No external calls, small data):** Given any test of this feature, When it runs, Then it makes no call to Wikimapia or OpenAI, uses no real API key, and uses only the trimmed fixtures already in `contracts/fixtures/wikimapia/` or small synthetic values (including the synthetic nested-replies example of AC-34); no bulk crawl output is used or committed.

## 4. Business Rules and Assumptions

1. **The Place Store receives Client data only.** Every save takes exactly what the Client returns (Listing Page, Place Details); the Place Store re-checks it against those shapes and the rules of this document before saving (AC-38, AC-39, AC-53) and never calls Wikimapia itself.
2. **Idempotent and all-or-nothing.** Saving the same data again changes nothing (apart from a later Details Fetched At, rule 5) and reports Unchanged (AC-9, AC-21, AC-22, AC-64). Every save either fully succeeds or leaves the Place Store exactly as it was (AC-15, AC-56, AC-58).
3. **Details take precedence over summaries (D1).** A Listing Save creates and updates Summary-Only Places in full. On a Detailed Place it only updates the Wikimapia Link; Place Name, Location and Outline of a Detailed Place come from its most recent Place Details. Details-only items are never changed by a Listing Save.
4. **Nothing seen is erased; Comments and Tags carry a Presence Mark (D2).** After a Details Save, the Comments and Place-Tag Links contained in the saved Place Details are Present, with the values and nesting given there. Stored Comments and Place-Tag Links of that Place that are not contained in them are kept, unchanged, and marked Gone. A Gone item contained in a later Details Save becomes Present again and takes the new values. No save ever removes a Comment, a Place-Tag Link or a Tag from the Tag Catalogue. Read-back returns Present and Gone items together, each with its mark (AC-71). Other details items (description, marks, Wikipedia link, Parent Place ID, address items) always follow the most recent Place Details (AC-24).
5. **Fetch moment (D3).** The Operator states Details Fetched At with each Details Save. A later moment with otherwise identical details only advances Details Fetched At and reports Unchanged.
6. **Nothing is decoded or trimmed.** Text is kept exactly as the Client reported it (HTML entities, line breaks, non-Latin letters, any length). Absent items stay absent; they are never stored as empty text or placeholders.
7. **Deleted is a mark, not a removal.** Places, Comments and Replies marked deleted or blocked by Wikimapia are kept with their marks. Wikimapia's marks and the Place Store's Gone mark are independent. What to show is decided by later stages.
8. **Privacy and licensing.** No Commenter IP is ever stored (`.agrules` section 4). Comment Authors are kept for every Comment, Present or Gone, and every Stored Place has a Wikimapia Link, for CC BY-NC-SA 3.0 attribution. The stored data is Wikimapia data, non-commercial only; no bulk export is part of this feature.
9. **Map shapes in WGS 84 (D4).** Outline Shapes and Centre Points use standard GPS longitude/latitude so Stage 2 can filter by area. Wikimapia's open Outlines of 3 or more points are closed for the shape; Outlines of fewer than 3 points get no Outline Shape. Outlines always read back as given.
10. **Schema changes only through Schema Setup.** Map-shape support and Vector Support are enabled by Schema Setup steps, never by hand (`.agrules` section 3). Embedding storage (substep 4) and crawl progress (substep 3) will be added by later Schema Setup steps.
11. **Parents are references, not requirements; Comments belong to their Place (D5).** A Parent Place ID may name a Place that is not stored (AC-30). Every Comment and Reply in a Details Save must carry the Place ID of the Place being saved; otherwise the save is Invalid Data. A Reply's Parent Comment is always a Comment of the same Place.
12. **Every Place has a Wikimapia Link (D6).** A Place first saved from Place Details gets the Built Link `http://wikimapia.org/<Place ID>`. A Listing Save sets the Listing Link on any Place, replacing a Built Link or an older Listing Link. A Details Save never changes a stored Wikimapia Link.
13. **Assumption:** concurrent saves of the same Place by two crawl jobs end with the Place matching one of the two saves in full, never a mix; this follows from rule 2 and is not tested separately in this feature.

## 5. Resolved Decisions

The stakeholder answered the six open questions of revision 1. No question remains open.

1. **D1, Summary vs details precedence (was Q1, default accepted):** Details win. A Listing Save on a Detailed Place only updates its Wikimapia Link; name, Location and Outline differences are ignored and do not count as a change. Affects AC-11, AC-20, AC-63, rule 3, glossary "Place Name".
2. **D2, Comments and Tags gone from Wikimapia (was Q2, alternative chosen):** Comments (including Replies) and Place-Tag Links missing from a newer Details Save are not deleted. They are kept with their last values and marked Gone; if they appear in a later Details Save they become Present again. Read-back returns all items together, each with its Presence Mark (the stakeholder asked for one approach; "return all with a mark" was chosen so a single read shows the full history and the embedding and search steps choose what to use). Re-saving the same data still changes nothing. Affects AC-2, AC-16 to AC-18, AC-21, AC-27, AC-49, AC-52, AC-56, AC-58, AC-59, new AC-64 to AC-69, AC-71, AC-72, rules 2, 4, 7, 8, glossary "Presence Mark", "Present", "Gone", "Place-Tag Link", "Save Outcome", US-4, US-9.
3. **D3, Details Fetched At on an unchanged re-fetch (was Q3, default accepted):** Identical details with a later fetch moment only move Details Fetched At forward; the save reports Unchanged. Affects AC-22, AC-64, rule 5.
4. **D4, Outlines with fewer than 3 points (was Q4, default accepted):** Saved with Centre Point and no Outline Shape; the Outline reads back exactly as given. Affects AC-48, new AC-70, rule 9, glossary "Outline Shape".
5. **D5, A Comment carrying another Place's ID (was Q5, default accepted):** Rejected as Invalid Data; nothing is saved. Storage tests of nesting use a synthetic example with matching Place IDs; the reconstructed nested-replies fixture is used only to test the rejection. Affects AC-34, AC-38, AC-62, rule 11, facts in section 0.
6. **D6, Wikimapia Link for a Place saved only from details (was Q6, alternative chosen):** The Place Store builds the link `http://wikimapia.org/<Place ID>` for such a Place. A later Listing Save's link replaces the Built Link (consistent with D1: a Listing Save updates the link); a Details Save never replaces a stored link, so a Listing Link is never downgraded to a Built Link. Affects AC-16, AC-18, AC-20, AC-31, AC-49, AC-59, new AC-63, rules 8 and 12, glossary "Wikimapia Link", "Listing Link", "Built Link", "Stored Place".
